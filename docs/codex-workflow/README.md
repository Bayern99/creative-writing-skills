# 《末班渡》工作流验证记录

## 原设计里谁作决定

检查基线为 上游 main，提交 f821366（0.9.5）。Mars 把代理与技能编译给不同宿主，Claude Code 版有具名代理。作者面对的 Muse 只在代理定义里声明职责、可用技能和可委派对象；实际流程写在技能里。因此移植时要沿着代理、技能和交接材料三层一起读。[Muse 定义](https://github.com/haowjy/creative-writing-skills/blob/f821366/agents/muse.md) · [生命周期](https://github.com/haowjy/creative-writing-skills/blob/f821366/skills/story-workflow/SKILL.md)

| main 中的职责 | Codex 版如何执行 |
| --- | --- |
| Muse 判断意图、区分已定与暂定、直接起草，拥有编辑裁决。作者决定方向与口味 | 当前会话担任 Muse。讨论和一般起草在本轮完成，冲突的专业意见由它回到文本核验 |
| Spark 轻量单人工作。Setup 由作者发起，先访谈再提案和写入 | 单人模式由 Muse 接受自然语言指定。初始化保留独立的 project-setup 入口 |
| 构思、人物模拟、大纲、文风和研究按问题分工；Writer 接另写一版、专门润色或很长的草稿 | 通过简报给通用子代理规定问题和材料。另一模型家族的结果取决于宿主是否真能提供；本次测试只验证独立上下文 |
| Critic 每人负责一种编辑层级或一个问题。连续性核查跨章节。Reader-sim 受读者可知信息限制 | 可并行核查同一稿件，再依次修订和试读。同一批报告算一轮，评读加修订满两轮就交还作者 |
| KB lead 在作品或决定已定时接手。试写与作者裁定分开 | 明确指出被接受的版本和授权的目标页。沿用已有条目；单独的审稿请求在审稿报告结束 |

原项目的生产者和审稿人简报规定了发什么、收什么；写作上下文指南还区分哪些角色需要前情、哪些角色只应看选出的资料。本版把这些规则放进 Muse 随包的分工说明。Meridian 的模型策略、跨提供商调度、知识库整树重组和外部同步超出本次改编与测试范围。[生产者](https://github.com/haowjy/creative-writing-skills/blob/f821366/skills/writing-staffing/resources/producers.md) · [审稿人](https://github.com/haowjy/creative-writing-skills/blob/f821366/skills/writing-staffing/resources/reviewers.md) · [交接材料](https://github.com/haowjy/creative-writing-skills/blob/f821366/skills/story-memory/resources/story-context.md) · [Codex 分工说明](../../plugins/creative-writing-skills/skills/creative-writing-muse/references/writing-staffing.md)

## 两种运行分别验证了什么

**本地 CLI 安装与发现。** 在空白配置目录用 Codex CLI 0.167.0-alpha.4 安装，app-server 的 skills/list 从插件缓存返回全部四个技能。检查 config.toml，新增内容只有市场位置及插件启用项。四个技能均配置为显式选用。Codex 文档说明本地可按用户或技能指令调用子代理；子代理继承当前权限和审批，模型与推理强度由现有设置决定。[Codex 子代理文档](https://developers.openai.com/codex/subagents/)

**行为验证。** 当前 Codex 宿主的主会话与真实子代理显式读取 CLI 安装缓存里的技能。以下是实际运行记录。在另一次尝试中，独立的 codex exec 在调用模型时收到 HTTP 401，因此本次没有验证桌面选择器到模型回答的完整链路，也没有运行 Claude Code 对照组。

### 一次普通的审稿请求

一个全新上下文的 Muse 收到第一、二章和普通作者请求：“第一章是定稿。请给第二章做一次独立的跨章连续性核查，也单独看看线索递到读者手里时会不会太早。我只要审稿，在聊天里交付，附一句你实际怎么分工的。” 测试向它指出安装后的 Muse 技能路径，未指定子代理名称或数量。

宿主实际建立了两条子会话。连续性审稿人并列引用“连红绳一起放进墙上的玻璃匣”和“解下颈间的红绳”；首次试读者指出，读到“刚好容得下一张船票”，自己已经猜到水渍的来历。Muse 核对原文并区分两处问题：钥匙需要解释或改动作；停航后的票可以是真线索，船是否真的开过仍待揭晓。交付止于聊天审稿。

### 从初稿到定稿归档

| 阶段 | 实际交接和结果 |
| --- | --- |
| 初稿审读 | 连续性角色读取第一章和第二章 v1。另一位编辑只读 v1 和希望保留怀疑的目标。前者定位钥匙矛盾，后者指出“刚好容得下一张船票”提前替读者量过水渍 |
| Muse 修订 | 按给定的作者简报，保留第一章定稿和折票习惯，把船票从柜中移到搪瓷杯下。现在可以擦水、挪杯、发现票，无需开柜；读者和阿芸同时错过核对水印的机会 |
| 盲读新版 | 用全新上下文，只给两章和首次试读方法。读者报告“我相信阿芸认得母亲的折法，至于这张票是谁折的、昨夜究竟有没有开船，我还拿不准。”盲读者没有获发作者的私下备选或审稿报告 |
| 定稿门槛 | 核对第一章、v1、作者简报和原设定页的 SHA-256，它们在修订和试读后保持原样。随后才提供单独的模拟作者定稿裁定，限定只写 canon.md |
| 归档暴露的问题 | 初版归档多记了桌沿变干以及早先章节的背景事实。收紧 story-memory：只提取本次接受范围里会约束后续写作的变化，先前章节用于核对。重测从同一份原始设定页开始 |

**可自行重走的材料。** 在一个空目录放入第一章、第二章 v1 和一份复制为 canon.md 的原设定页。先用上述请求只做审稿；若要测试改稿，再给作者简报。试读者只读前文及第二章 v2。最后才提供定稿裁定，比较设定页的增量。[第一章](chapter-1.md) · [第二章 v1](chapter-2-v1.md) · [作者简报（含备选）](decision.md) · [第二章 v2](chapter-2-v2.md) · [原设定页](canon-before.md) · [模拟定稿裁定](acceptance.md)

**归档复测。** 同一份定稿和裁定在重新安装的技能上只新增了一条第二章记录，保留船票及折角记忆，放票人和是否开船都留白。再用相同输入执行一次，返回零项增量，归档文件的 SHA-256 校验一致。[实际归档结果](canon-after.md)

**单人和两轮上限。** 另开一个 Muse 会话，给它 v2，并把“已完成两轮，本次你自己看，只说口味取舍”作为测试前提。该会话没有派子代理，只问结尾希望读者更惦记母亲还是水渍。这验证了到达上限时的行为；测试没有让宿主从零连续生成两轮修订。
